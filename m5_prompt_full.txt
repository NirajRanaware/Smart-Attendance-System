# 3. RETRY AND FAILURE HANDLING

Verify the established retry policy:

| Parameter | Required value |
|---|---|
| Base delay | 15 seconds |
| Exponential multiplier | 2 |
| Jitter | ±10% |
| Maximum delay | 900 seconds |
| Maximum retry attempts | 5 |

Test these scenarios:

- Google API timeout.
- Internet connection failure.
- HTTP 429 rate limit.
- HTTP 500, 502, 503 and 504.
- Authentication failure.
- Permission denied.
- Invalid spreadsheet ID.
- Missing credentials.

Requirements:

- Temporary errors must be retried.
- Permanent errors must be classified correctly.
- Exhausted records must enter `dead_letter`.
- No record should remain permanently stuck in `in_progress`.
- Error messages must be useful for troubleshooting.
- Credentials and private keys must never appear in logs.

# 4. DUPLICATE PREVENTION

Verify and strengthen the existing Attendance ID-based duplicate prevention.

Test:

1. Normal successful synchronization.
2. Repeated synchronization attempts.
3. Google accepts an append but the client receives a timeout.
4. Worker restarts after an uncertain API response.
5. Existing Attendance ID is already present in Google Sheets.
6. Multiple workers process different batches.

Requirements:

- Attendance ID must remain the unique synchronization identifier.
- Existing Google Sheets records must not be appended again.
- A record already present in Google Sheets must be marked synced locally.
- An uncertain API response must not cause silent data loss.
- Never delete authoritative SQLite attendance records.

# 5. WORKER CRASH AND RECOVERY TESTING

Simulate:

- Worker termination during synchronization.
- Worker restart after a claimed batch.
- Expired lease recovery.
- Database connection interruption.
- Google API unavailability during a batch.

Verify:

- Unfinished records are recoverable.
- Active leases are not incorrectly reclaimed.
- Expired leases return to an eligible state.
- No attendance records are lost.
- The worker can resume processing after restart.

# 6. DEAD-LETTER MANAGEMENT

Inspect existing dead-letter functionality.

Determine whether administrators can:

- Identify dead-letter records.
- View their attendance IDs.
- View the last synchronization error.
- Identify retry counts.
- Distinguish permanent errors from exhausted transient errors.

If an administrative recovery mechanism is missing, implement a safe mechanism allowing authorized administrators to retry selected dead-letter records.

Security requirements:

- Admin authentication required.
- CSRF protection required for state-changing requests.
- POST/PATCH methods only for state changes.
- Never expose credentials.
- Never delete attendance records during recovery.

Do not add unnecessary UI features if an existing protected administrative mechanism already provides equivalent functionality.
